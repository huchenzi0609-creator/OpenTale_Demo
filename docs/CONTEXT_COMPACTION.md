# 模型输入压缩与恢复

本文说明反身实验 v2 的模型输入投影：如何缩小单次请求，如何保留完整材料，以及升级后怎样继续未完成阶段。自动化验证使用合成材料与本地夹具；另对用户报告的失败恢复点在本机只读重编译，只报告聚合尺寸，不输出原文，不调用付费模型。

## 两种容量需要分别理解

实验的累计调用数、累计 token 和窗口数由存档里的预算控制，可以设为无限。模型单次能够接收的上下文仍有实际容量。

一个材料被多个视图、候选对象、方法和阅读历史引用时，向模型发送的 JSON 可能重复携带同一段文字。原文长度与最终请求长度因而不是同一个量。增加累计 token 预算无法解决单次请求过长。

输入压缩处理单次请求的表示方式，不修改实验的累计预算，也不更换模型或自动发起额外的摘要模型调用。

## 完整材料与模型投影

程序保存的冻结输入和发给模型的投影分别承担不同职责：

- 冻结输入保存该作业原有的材料、视图、编号与权限，供校验、重试和回放使用。
- 模型投影在这些已获准的材料之内选择紧凑表示，保留可追踪的来源与引用关系。
- 实际模型请求体独立计算 hash，并作为逐次调用证据保存。

压缩不会用删节后的内容覆盖人物 Markdown、共享表达、既有正文或存档中的完整材料。完整内容仍由原来的材料存储与本地读取机制保存；能否读取某个对象继续服从原有作用域权限。压缩不会给其他位置新增私人资料访问权。

本地对象接口可通过 `GET /api/runs/{run_id}/objects?scope_id=...&query=...` 检索当前作用域可见材料，通过 `GET /api/runs/{run_id}/object?scope_id=...&object_id=...` 取得可见对象的完整内容。精确旧版本由方法执行时的对象解析器处理。存在完整内容的取回机制，不意味着每次模型调用都会自动重新读取全部省略内容。

当前采用确定性的材料整理和文本摘录。它可以保留来源、结构与可见引用，但**不能保证语义无损**：省略的文本可能包含关键转折，保留下来的片段也可能改变读者对上下文的理解。它不是经过另一个模型全面归纳、逐条核实的长期记忆摘要。

## 压缩实际怎样发生

新 DeepSeek 投影仅为 `reflexive_v2` 的输入启用压缩。经典模式、第一版反身实验和旧投影适配器保持原来的请求表示。

当原始请求超过目标尺寸时，`providers/context.py` 执行 `source-excerpts-v1`：

1. 将相同文本放入共享 `text_pool`，各材料出现位置通过 `text_ref` 引用它。重复元信息在能够节省空间时进入 `material_metadata`，各位置用 `metadata_ref` 还原原有字段。材料的出现次数、顺序、作用和视图结构保留；相同文字在两个位置出现，仍有两个组织上的位置。
2. 候选目录保留整数接口、对象类型与版本；历史视图和方法的目录改为结构概览。已执行的完整方法定义进入去重池，检查与调用记录仍各自保留。
3. 如果还超过目标，对选中材料和阅读历史分配摘录额度，保留完整语句或段落片段。每份文字优先保留首尾，内部片段参考当前组织指令与焦点中的词项。主体背景、局部回应和组织后果权重较高；最近两段阅读历史获得更高优先级。
4. 每份摘录记录原文 hash、原始长度、保留的字符区间、片段内容和省略字符数。区间采用包含起点、不包含终点的表示。

系统不会把不相邻的片段伪装成连续原文。优先保留完整语句；个别超长、无分隔的单句需要按字符范围摘录时，额外标记 `partial_sentence=true`。模型同时得到输入说明，知道哪些内容只是摘录；输出仍使用原来的自然语言字段，不能把 `text_ref` 等输入表示写进正文。

目标是柔性的：完整长句、必要接口或组织定义本身可能超过分配额度。不能在保证结构和引用有效的前提下缩小时，依然可能在发送前返回 `CONTEXT_TOO_LARGE`。压缩不能替代方法对读取范围的选择，也没有增加模型本身的上下文容量。

如果接口和结构本身已占满柔性目标，程序优先保留去重后的完整文字，并标记 `within_target=false`；只有接近实际请求容量时才按可用空间继续摘录。因此，较小的目标值不会无条件把所有来源挤成几句标签。未超过目标的短输入保持原有表示。

## 配置和压缩记录

`OPENTALE_CONTEXT_TARGET_CHARS` 设置单次输入的目标字符数，默认 **96000**。单位是字符，不是 token；不同文字与不同模型的 token 换算有差异。它是触发输入整理的目标，不是累计消耗上限。服务端还会为格式修复说明保留空间，并继续检查最终传输大小。

压缩请求的用户 JSON 中包含 `context_compaction`，请求封套保存对应摘要，包括：

| 字段 | 含义 |
| --- | --- |
| `algorithm` / `projection_version` | 摘录算法与请求表示版本 |
| `input_chars` / `output_chars` / `target_chars` | 压缩前、压缩后的基础请求尺寸及目标尺寸 |
| `material_occurrences` / `text_entries` | 材料出现次数与去重后的文本数量 |
| `original_text_chars` / `retained_text_chars` / `omitted_text_chars` | 文本池中原文、保留与省略的字符量 |
| `lossy` | 文本池中的文字是否发生省略；候选目录本身仍可能是已标注的概览 |
| `history_segments_excerpted` | 采取摘录的阅读历史段数 |
| `within_target` | 基础请求是否落在柔性目标内 |

格式修复的提示会增加最终请求长度，所以逐次尝试另记实际 `request_chars`；它与基础压缩尺寸不一定相等。修改压缩目标会改变未来请求，不能据此重新标注已经冻结的旧请求。

## 投影版本与恢复

每个反身实验 v2 请求保存 `projection_version`。兼容适配器使一个已冻结、尚未接受结果的请求继续使用其原投影版本。

新投影版本标识为 `provider-json-v2-context`；旧请求使用 `provider-json-v1`。版本选择不能只影响存档里的字符串：实际的请求构造也必须使用同一适配器。

恢复存在两种情况：

1. **在本地投影检查时就被拒绝，尚未产生请求封套。** 后续可使用新投影处理同一冻结输入。其他已经接受的结果原样保留，只补做缺失的作业。
2. **已经有冻结请求和尝试记录，但尚未接受结果。** 使用该请求保存的旧投影版本，保留原 request hash 和 frame hash。不能把旧请求改名成新版本，不能静默覆盖其请求体。

已经接受的提案、续写与阅读结果会从待运行清单中跳过。成功请求封套、尝试证据及结果 hash 都不会因升级被重写。

这也有明确边界：若一个旧请求必须使用旧投影，而旧投影本身无法满足请求容量，程序不能假装已经按新内容重试。这样的情况需要显式的新请求版本／干预过程，不能通过清空整个窗口或删除旧证据来恢复。

## 本地拒绝与费用记录

网络发送前的投影失败不是模型调用，不应增加调用数或把估算值记为未知 token。反复点击恢复也不应因此重复计费或重新生成已经接受的内容。

真正已经发出的请求遵循原有记账规则：有可信用量就记录实际用量；网络中断且用量未知时保留未知占用。输入压缩不允许把这些历史消耗清零。

## 证据与回放

输入证据核对四件独立的事：

1. 冻结的完整输入是否与其 frame hash 相符。
2. 各次发送的实际投影是否与该次 request hash 相符。
3. 接受的结果是否与提案、续写或阅读事件中的结果 hash 相符。
4. 文本池中的片段、原文 hash、字符范围和各次材料出现位置，是否与冻结输入中的原始值一致。即使人为重算请求 hash，也不能让虚构摘录通过来源核验。

语义回放使用冻结输入和已接受的关系操作，不再次调用远程模型，也不要求新程序重新生成历史上的模型输出。因此，保留原 frame 并完整记录新投影，是继续验证历史行为的前提。

格式修复和投影升级是不同的事件。不能给某次调用加上格式修复标签，借此绕过投影版本及请求 hash 的检查。

严格配对实验另有程序／模型配置签名。代码升级后若签名变化，其保护仍然有效；普通存档能够恢复，不代表升级前后的两条分支仍然构成同条件对照。

## 离线验收

`tests/test_context_runtime.py` 使用三个或八个合成叙述位置，检查：

- 除一个位置外的提案已经接受，而最后一个在网络发送前被拒绝。
- 重复本地拒绝不增加调用次数、未知 token 或已接受位置的调用。
- 新投影恢复后只补做缺失提案，随后正常完成续写与阅读阶段。
- 原冻结 frame hash、旧成功请求与旧提案事件保持一致。
- 旧未接受请求由版本适配器继续使用完全相同的请求投影。
- 保存重载、请求证据校验与语义回放通过。

这些验证说明恢复和证据机制保持一致，不能证明摘录没有遗漏任何叙事含义。真实模型的材料利用、关系保持和长篇效果仍需独立观察。
